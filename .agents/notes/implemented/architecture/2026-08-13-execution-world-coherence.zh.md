# Agent Note: 执行环境一致性

Status: implemented

[English](2026-08-13-execution-world-coherence.md) | 中文

## 问题

文件工具通过 `ctx.fs` 操作，而搜索、Shell、LSP、任务、MCP stdio、Git 子进程与 PTY 分配最终使用 `ctx.subprocess`。提供方替换依赖组合约定来保持这两个根能力一致。混合本地与远程，或者混合两个远程实例时，系统可能读取和编辑一个项目，却在另一个位置执行命令。

## 决策

每个文件系统与子进程提供方都暴露一个不透明、仅在进程内有效的执行环境身份。发行组合挂载启动守卫；只有两个身份是同一个对象时，提供方才能完成激活。标签只用于诊断，不能建立等价关系。

宿主本地提供方共享一个导出的身份。由远程所有者支持的适配器暴露该所有者的实例身份，因此同一提供方类型创建的两个独立沙箱仍是不同环境。

身份检查把共同位置变成启动不变量，同时不会让消费方耦合到本地、SSH、容器、E2B 或未来的 Kubernetes 实现。它也为远程 Inventory 条目提供了具体规则：所有能力适配器必须由同一个已解析环境所有者构造。

## 考虑过的替代方案

**比较提供方标签或类型。** 拒绝，因为同一提供方创建的两个容器或远程主机仍是不同环境。

**依赖 bundle 组合。** 拒绝，因为用户 overlay 与未来 Inventory 解析都可以单独替换一个提供方。

**把所有能力合并为一个大型服务。** 拒绝，因为文件系统与进程提供方独立演化，现有消费方也已依赖各自的窄 seam。

## 后果

不透明身份只能证明参与该约定的提供方。绕开两个根能力的提供方特有能力需要自己的身份检查。进程内对象也不能替代分布式控制平面的持久环境 ID；控制平面先解析持久 ID，再创建共享同一个运行时对象的适配器。

单元覆盖证明同一对象可通过，并拒绝标签相同但对象不同的身份。已组装的 base profile 在本地文件系统与子进程提供方上挂载守卫；构建与 Loader 验证覆盖该产品路径。
