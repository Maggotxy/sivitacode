# Agent Note：健康门控滚动发布

Status: implemented

[English](2026-08-14-health-gated-rollouts.md) | 中文

## 问题

从浏览器调用多个独立部署 plan 不能形成一个持久的多节点决策。否则控制平面重启、并发执行请求、目标修改或早期节点失败，都可能在没有权威 rollout 记录的情况下让后续节点继续运行。

## 决策

Inventory 持有独立于单目标 plan 的 rollout 记录。创建时固定 2–64 个唯一目标的有序集合、每个已观察 revision 与环境、一个字面 argv、超时，以及一到十六的批次大小。actor 必须对每个目标拥有 `operate`。只要包含任一生产成员，完整 rollout 就必须由另一名对全部成员拥有 `administer` 的管理员审批。

执行使用与 plan 审批和预留相同的串行变更 owner。它把一个已观察的 ready revision 原子转换为 running，拒绝任何已变更或停用的成员，然后按保存顺序处理有界批次。每个目标都在执行前即时接受健康检查。批内成员可以并发；只有全部成员成功后才启动下一批。健康或命令失败会把对应成员结算为 failed，并把所有尚未启动的成员标记为 skipped。逐目标输出沿用有效 UTF-8 的 64 KiB 上限。

除部署 argv 外，每个 rollout 还可持久保存摘流、部署后验证、回滚和恢复流量 argv。配置摘流时必须配置恢复。Inventory 按顺序执行生命周期，在部署或验证失败后尝试回滚，并在摘流成功后始终尝试恢复。每个阶段都有独立的有界持久结果。恢复失败或摘流后重启会产生 `recovery-required`；恢复操作只重试恢复命令，绝不会通过重新部署来猜测结果。

Web 客户端通过添加、移动和移除控件构建显式顺序队列。它把可见队列直接发送给 Inventory，因此浏览器选项排序不会改变 rollout 顺序。

服务重启会把 running 成员结算为 failed，把 pending 成员标记为 skipped。未结算 rollout 会阻止删除任何成员。列表可见性要求对完整成员集合拥有 read，因此局部授权不会泄露其余拓扑。

## 考虑过的替代方案

**在 Web client 中创建多个普通 plan。** 不采用，因为浏览器状态不是执行事务，无法持有重启恢复或 exactly-once 预留。

**某批失败后继续。** 初始策略不采用，因为后续节点会在已有负面健康信号时仍收到发布。未来策略可以显式增加失败预算，而不是削弱该默认值。

**并发运行全部目标。** 不采用，因为这会消除 rollout 的运维价值，并可能同时关闭全部副本。

## 后果

SivitaCode 可以在本机、固定密钥 SSH 与 rootless 容器目标之间执行显式、带审批且并发有界的滚动发布。该机制是 fail-stop 而不是自动回滚：应用特定回滚由部署 argv 持有，持久记录则精确标识 succeeded、failed 与 skipped 成员。定时触发和负载均衡摘流 hook 仍属于独立消费方。
