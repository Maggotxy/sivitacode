# Agent Note：SivitaCode 持久访问控制

Status: implemented

[English](2026-08-14-sivitacode-persistent-access-control.md) | 中文

## 问题

SivitaCode 的公网 Web 控制平面使用独立访问控制服务，而不把启动口令当作身份数据库。该服务基于 domain 存储形式持有持久用户、Argon2id 密码凭据、随机服务端会话、用户会话版本、禁用状态、内置角色、请求局部 actor 与追加式审计记录。

## 决策

Web 认证插件只负责 HTTP 事项：可信反向代理校验、登录和退出路由、Cookie、限流，以及把访问控制服务验证的 actor 绑定到传输请求。浏览器从不提供角色。连接 carrier 恢复该 actor，进入 `AsyncLocalStorage` 作用域，并在分发 API 或 WebSocket 工作前检查由服务端选择的操作权限。因此并发异步工作能够携带授权身份，而无需把可变身份放到进程级 API 服务上。

PWA manifest 与产品 favicon 会先经过相同的请求 authority 校验，再免除会话认证而公开。它们只包含安装元数据；精确公开这两个路径，使浏览器能安装受登录保护的应用并呈现品牌，同时不会暴露前端 bundle、API 或项目数据。

初始环境用户名与密码是引导输入。它们仅在持久用户表为空时创建首个管理员；密码会立即经 Argon2id 变换，账户库存在后环境值不再具有控制权。禁用用户会增加会话版本，因此先前签发的全部会话都会验证失败，无需先扫描或逐条删除会话记录。

初始角色对应当前 Host 操作组：viewer 可读，developer 可读并操作智能体任务，operator 还可更改配置，admin 还可管理身份。持久格式不会预设项目授权或外部身份提供方。这些能力可在以后提供新的策略实现，而不会削弱当前默认拒绝的操作检查。

## 考虑过的替代方案

**保留环境口令和进程局部会话。** 拒绝，因为跨重启撤销、多用户身份、密码加固升级和审计无法建立在临时 Map 上。

**把角色放进浏览器 RPC 载荷。** 拒绝，因为不可信客户端可以自报权限，并迫使每个消费者重复验证身份。

**把可变 actor 存在进程级 API 服务上。** 拒绝，因为并发 HTTP 与 WebSocket 工作会竞态，并可能在另一个请求的身份下执行。

## 后果

验证覆盖 Argon2id 登录、持久重开、请求会话解析、服务操作内部权限拒绝、禁用用户撤销、审计创建、Web 登录与退出、登录限流、公开安装元数据、可信反向代理校验，以及仓库类型、lint、文档和组装门禁。
